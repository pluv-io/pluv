## Room

`createRoom` returns the room. It holds the document, the treaty, and the listeners.

## Session manager

`manageSessions` attaches the session manager to a room. It holds the sockets and writes frames. `register`, `onMessage`, `onClose`, `onError`, `broadcast`, `evict`, and `garbageCollect` are called on the session manager. The [IO reference](/docs/api-reference/io) lists those methods.

## Frame

A frame is one message written to a socket. It has a type and a payload.

### Broadcast frame

A broadcast frame is written to every connection, including the sender. Document changes travel in these frames, and every connection applies them from here.

### Self frame

A self frame is written only to the sender. It is that message's reply. The other connections do not receive it.

## Deferred result

A deferred result is a handler that is still waiting. It has no frames yet. The session manager lets the next message run. When that handler finishes, the room returns an effect. [Messages](/docs/infrastructure/messages) shows what happens while that handler is still waiting.

## Effect

An effect is the finished result of a handler. It carries the broadcast frames, the self frames, and whether the in-memory document is ahead of the snapshot. The room stops there. The session manager writes the frames. Those broadcast frames carry the document changes. The room keeps a list of changes the clients have not received yet, and takes off that list the changes this broadcast sent, so a later [snapshot](#snapshot) does not send them again. [Messages](/docs/infrastructure/messages#effect) shows why a second send would apply the same change twice.

When the room and the sockets live in different places, see [Hosted rooms](/docs/infrastructure/hosted).

## Snapshot

A snapshot writes the whole document into the server's storage. The document clients are editing stays in memory. The snapshot matters when that memory is gone, because the next start loads the document from the server's storage:

- A Cloudflare Durable Object hibernates. The next time it wakes, it loads the document from the Durable Object's storage.
- A Node.js server crashes. The restarted process loads the document from the server's storage.

The room calls `getInitialStorage` only when the server's storage has no document.

This is a different write from the one an app configures for its own database. `onStorageSnapshot` runs after the document is written to the server's storage. `onStorageDestroyed` runs when the document is about to be destroyed. Those listeners are where the app keeps its own copy. The snapshot does not wait for `onStorageSnapshot`. [Loading storage](/docs/guides/storage/loading) shows those listeners.

While clients are still connected, the snapshot also sends a broadcast frame for a change they have not received yet. [Messages](/docs/infrastructure/messages#snapshot) shows when that write waits.
